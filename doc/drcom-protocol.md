# Drcom 协议分析

基于 JLU 校园网 Drcom 认证协议的逆向分析，结合 `cygnus-rs` 项目实现整理。

## 概览

Drcom 协议通过 UDP 与认证服务器通信，默认服务器地址 `10.100.61.3:61440`。认证流程分为三个阶段：

1. **Challenge（挑战）** — 向服务器请求 salt 和客户端 IP
2. **Login（登录）** — 提交加密后的用户凭证完成认证
3. **Keep Alive（心跳保活）** — 持续发送心跳包维持连接

## 1. Challenge 阶段

### 请求包

| 偏移 | 长度 | 值 | 说明 |
|------|------|----|------|
| 0 | 1 | `0x01` | 包类型：Challenge |
| 1 | 1 | `0x02 + try_times` | 第几次尝试（从 0 开始） |
| 2 | 2 | 随机数 | 2 字节随机数 |

总共 20 字节，不足部分用 0 填充。

最多重试 5 次。

### 响应包

| 偏移 | 长度 | 说明 |
|------|------|------|
| 0 | 1 | 包类型标识，`0x02` 表示成功 |
| 4 | 4 | **salt** — 用于后续登录加密 |
| 20 | 4 | **client_ip** — 服务器分配的客户端 IP |

接收方校验 `recv_buf[0] == 0x02`，成功则提取 salt 和 client_ip。

## 2. Login 阶段

### 登录包构造

登录包是一个 ~334 字节的变长数据包，结构如下：

| 偏移 | 长度 | 说明 |
|------|------|------|
| 0 | 3 | `[0x03, 0x01, 0x00]` 固定头 |
| 3 | 1 | `username长度 + 20` |
| 4 | 16 | **md5a** — 见下方加密算法 |
| 20 | 36 | 用户名（不足 36 字节用 0 填充） |
| 56 | 2 | `[0x20, 0x05]` |
| 58 | 6 | `md5a前6字节 XOR mac` |
| 64 | 16 | **md5b** — 见下方加密算法 |
| 80 | 1 | `0x01` |
| 81 | 4 | client_ip |
| 85 | 12 | 全 0 |
| 97 | 8 | **md5c** 前 8 字节 — 见下方加密算法 |
| 105 | 1 | `0x01` |
| 106 | 4 | 全 0 |
| 110 | 32 | 主机名（不足 32 字节用 0 填充） |
| 142 | 4 | `[10, 10, 10, 10]` |
| 146 | 4 | `[10, 10, 10, 10]` |
| 150 | 4 | `[10, 10, 10, 10]` |
| 162 | 1 | `0x94` |
| 166 | 1 | `0x06` |
| 170 | 1 | `0x02` |
| 174 | 2 | `[0xf0, 0x23]` |
| 178 | 1 | `0x02` |
| 182 | 9 | DrCOM 魔数 `[0x44, 0x72, 0x43, 0x4f, 0x4d, 0x00, 0xcf, 0x07, 0x6a]`，即 ASCII `"DrCOM"` + `\0` + `0xcf, 0x07, 0x6a` |
| 246 | 40 | 固定哈希字符串 `"1c210c99585fd22ad03d35c956911aeec1eb449b"` |
| 310 | 1 | `0x6a` |
| 313 | 1 | password 长度（最大 16） |
| 314 | password_len | **ror 加密后的密码** — 见下方加密算法 |
| 314 + len | 2 | `[0x02, 0x0c]` |
| 316 + len | 4 | **checksum** — 见下方加密算法 |
| 320 + len | 2 | `[0x00, 0x00]` |
| 322 + len | 6 | MAC 地址 |
| 328 + len | 变长 | 对齐填充 + 2 字节随机数 |

最终包长度 = `334 + password_len - 1`

### 响应包

| 偏移 | 说明 |
|------|------|
| 0 | `0x04` 表示登录成功 |
| 23..39 | **tail** — 用于心跳包的 16 字节令牌 |

错误响应：
- `0x05` + byte 4 为 `0x0b` → MAC 地址无效
- `0x05` + 其他 → 用户名或密码错误

## 3. 加密算法

### 3.1 md5a

```
md5a = MD5([0x03, 0x01] + salt + password_bytes)
```

16 字节结果，用于填充登录包偏移 4-19 以及与 MAC 进行 XOR。

### 3.2 md5b

```
md5b = MD5([0x01] + password_bytes + salt + [0x00; 4])
```

16 字节结果，填充登录包偏移 64-79。

### 3.3 md5c

```
md5c = MD5(login_data[0..97] + [0x14, 0x00, 0x07, 0x0b])
```

取 md5c 的前 8 字节填充登录包偏移 97-104。

### 3.4 ror（密码加密）

对密码的逐字节操作：

```
for each byte i:
    x = md5a[i] XOR password[i]
    result[i] = (x << 3) + (x >> 5)   // 循环左移 3 位
```

将 ror 结果写入登录包偏移 314 处，写入长度为 `min(password_len, 16)`。

### 3.5 checksum

```
data = [0x01, 0x26, 0x07, 0x11, 0x00, 0x00] + mac_bytes

处理方式：
1. 每 4 字节做 XOR，不足 4 字节右对齐补 0
2. 结果视为小端 u32，乘以 1968
3. 转为大端 4 字节输出
```

### 3.6 crc（心跳包校验）

```
data 每 2 字节一组: sum ^= (byte2 << 8 | byte1)
输出为小端 4 字节
```

## 4. Keep Alive 心跳阶段

登录成功后进入无限循环，每 20 秒发送一轮心跳。每轮心跳包含以下步骤：

### 4.1 心跳类型 38（长度固定 38 字节）

| 偏移 | 长度 | 说明 |
|------|------|------|
| 0 | 1 | `0xff` |
| 1 | 16 | md5a |
| 20 | 16 | tail（登录响应中的令牌） |
| 36 | 2 | 随机数 |

响应中偏移 28-29 提取 **keep_alive_version**，用于后续 40 字节心跳包。

### 4.2 心跳类型 40（长度固定 40 字节）

| 偏移 | 长度 | 说明 |
|------|------|------|
| 0 | 1 | `0x07` |
| 1 | 1 | keep_40_count（递增计数器） |
| 2 | 1 | `0x20` |
| 3 | 1 | `0x00` |
| 4 | 1 | `0x0b` |
| 5 | 1 | 类型标识：EXTRA=`0x0f` 保持不变，FIRST/SECOND 根据 keep_alive_version 填充 |
| 6 | 2 | keep_alive_version（EXTRA 时为 `[0x0f, 0x27]`，否则为服务器返回的版本号） |
| 8 | 2 | 随机数 |
| 16 | 4 | tail_2（SECOND 类型心跳响应中提取） |

SECOND 类型额外计算：
- 偏移 24-27 填入 `crc(data[0..24] + client_ip)`
- 偏移 28-31 填入 `client_ip`

### 4.3 心跳流程

每轮循环：

```
1. 发送 38 字节心跳包
2. 接收响应，更新 keep_alive_version
3. 每 21 轮发送一次 EXTRA 类型的 40 字节心跳包
4. 发送 FIRST 类型的 40 字节心跳包，接收响应，提取 tail_2
5. keep_40_count++
6. 发送 SECOND 类型的 40 字节心跳包
7. keep_40_count++
8. 等待 20 秒
```

## 5. 用户数据文件格式

用户凭证通过 AES-256-GCM 加密后存储为 `.usr` 文件，格式为：

```
[32 字节: AES 密钥] → AES-256-GCM 密钥
[12 字节: Nonce]     → AES-256-GCM Nonce
[8 字节: 长度]       → 加密后密码的字节长度（大端 u64）
[N 字节: 加密密码]   → AES-256-GCM 加密的密码明文
[8 字节: 长度]       → 用户名的字节长度（大端 u64）
[M 字节: 用户名]     → UTF-8 编码的用户名
[6 字节: MAC]        → 6 字节 MAC 地址
```

密钥和 Nonce 在加密时随机生成，以明文存储在文件头部，解密时直接读取。密码使用 AES-256-GCM 的 `aes-gcm` crate 加解密。
